# Incident Response Exercise 01 — PowerShell Network Alert

## Case Objective

The objective was to investigate the PowerShell network alert generated during the Week 7 alerting exercise.

The alert was generated by the Splunk saved search:

```text
SOC - PowerShell Network Connection
```

The alert identified PowerShell processes establishing outbound network connections.

## Initial Alert

The alert was triggered by controlled laboratory activity involving:

```text
User: Administrator
Process: powershell.exe
Destination: 8.8.8.8
Hostname: dns.google
Destination Port: 443
Protocol: TCP
```

The event occurred on:

```text
2026-09-21 09:57:32.773
```

## Investigation

The network event was correlated with a PowerShell process creation event.

The relevant process information included:

```text
ProcessId: 4196
ProcessGuid: {12dcad69-fd16-6ab0-3103-000000006a00}
Parent Process: explorer.exe
```

The activity was associated with the controlled test:

```powershell
Test-NetConnection 8.8.8.8 -Port 443
```

This established a direct relationship between the alert and an intentionally generated test event.

## Timeline

The investigation established the following sequence:

```text
Controlled PowerShell execution
        ↓
Test-NetConnection
        ↓
Outbound TCP connection
        ↓
8.8.8.8:443
        ↓
Splunk telemetry
        ↓
SOC alert triggered
        ↓
Analyst investigation
```

## Evidence Assessment

The network connection itself was not sufficient to classify the activity as malicious.

Additional evidence showed:

* Controlled laboratory testing
* PowerShell process creation
* Expected destination
* Matching process context
* No identified malicious indicators

## Disposition

**Expected / Benign controlled laboratory activity**

The alert functioned as designed and successfully identified the controlled PowerShell network behavior.

## Analyst Lesson

This exercise demonstrated that a SOC analyst should investigate the context behind an alert rather than assuming that every alert represents a confirmed security incident.

# Incident Response Exercise 02 — Unknown Process Network Activity

## Case Objective

The objective was to investigate a network connection where process attribution was incomplete.

## Initial Finding

The network event involved:

```text
Destination IP: 20.42.179.192
Destination Port: 443
ProcessId: 1656
ProcessGuid: {00000000-0000-0000-0000-000000000000}
```

The all-zero ProcessGuid created an attribution challenge.

## Initial Correlation

A `taskhostw.exe` process using PID `1656` was identified shortly before the network event.

The timing suggested a possible relationship, but PID matching alone could not establish process identity.

The taskhostw process had a different ProcessGuid.

## ProcessGuid Investigation

The exact ProcessGuid associated with the identified taskhostw process was searched across the available telemetry.

No matching network event was found for that exact ProcessGuid.

This meant that the network event could not be confidently attributed to that process instance.

## Timeline Consideration

The investigation demonstrated why both time and process identity are important.

The approximate sequence was:

```text
taskhostw.exe process activity
        ↓
approximately 2.3 seconds
        ↓
network connection
        ↓
20.42.179.192:443
```

The close timing justified further investigation but did not prove causation.

## Evidence Assessment

The investigation identified several limitations:

* All-zero ProcessGuid on the network event
* PID reuse possibility
* Different ProcessGuid values
* Lack of exact ProcessGuid correlation
* Insufficient evidence for definitive process attribution

## Disposition

**Needs Context / Telemetry Attribution Gap**

No confirmed malicious activity was identified from the available laboratory telemetry.

The case was documented as an attribution limitation rather than automatically classified as malicious.

## Analyst Lesson

This investigation demonstrated an important incident-response principle:

> Correlation requires reliable identifiers, not simply similar timestamps or matching PIDs.

ProcessGuid provides stronger evidence for process-level correlation when available.

# Incident Response Exercise 03 — PowerShell Compatibility Activity

## Case Objective

The objective was to investigate PowerShell execution associated with Windows compatibility telemetry.

The investigation focused on determining whether the PowerShell activity represented suspicious execution or expected Windows system activity.

## Initial Finding

The relevant PowerShell process was observed on:

```text
2026-09-25 10:41:58.453
```

Process information included:

```text
Process: powershell.exe
User: SYSTEM
ProcessId: 5524
Parent Process: CompatTelRunner.exe
ProcessGuid: {12dcad69-4ff6-6ab6-ac01-000000006b00}
```

The command line included:

```text
powershell.exe -ExecutionPolicy Restricted -Command ...
```

The command performed Windows system information and network-adapter related queries, including:

```text
Get-VMSwitch
Get-NetLbfoTeamNic
```

## Parent Process Investigation

The parent process was:

```text
CompatTelRunner.exe
```

Additional telemetry showed scheduled Windows compatibility activity surrounding the PowerShell execution.

This provided important context for the investigation.

## Process Correlation

The exact ProcessGuid was searched across the available telemetry.

The search identified the Event ID 1 process creation event but did not identify a corresponding Event ID 3 network connection for the exact ProcessGuid.

Additional searches for file and registry activity associated with the ProcessGuid did not identify related activity.

## Indicator Review

The command line and surrounding telemetry were reviewed for indicators such as:

```text
EncodedCommand
ExecutionPolicy Bypass
WindowStyle Hidden
```

No investigated suspicious indicators were identified.

The observed command used:

```text
ExecutionPolicy Restricted
```

rather than a bypass configuration.

## Evidence Assessment

The investigation identified:

* SYSTEM account
* Windows compatibility parent process
* Restricted PowerShell execution policy
* Expected system-information commands
* No matching network event for the exact ProcessGuid
* No identified encoded or hidden execution indicators
* Supporting scheduled Windows telemetry

These findings provided contextual evidence for expected system activity.

## Disposition

**Expected / Benign Windows system activity**

The available telemetry did not provide evidence that the PowerShell activity represented malicious execution.

## Analyst Lesson

This exercise demonstrated why parent-process context is important during PowerShell investigations.

PowerShell is a legitimate Windows administration and automation tool. Its presence should therefore trigger contextual investigation rather than an automatic malicious classification.

# Incident Response Methodology

The incident-response exercises followed a repeatable investigation methodology.

## 1. Identify

The analyst first identified the alert or suspicious event requiring investigation.

Examples included:

* PowerShell network alert
* Unknown process network connection
* SYSTEM PowerShell execution

## 2. Collect Evidence

Relevant telemetry was collected from Splunk.

Evidence included:

* Event ID
* Timestamp
* Image
* User
* ProcessId
* ProcessGuid
* Parent process
* Command line
* Network destination
* Network port
* Protocol

## 3. Build a Timeline

Events were placed into chronological order to understand what happened before, during, and after the suspicious activity.

## 4. Correlate Events

Correlation used:

* ProcessGuid
* ProcessId
* Timestamp
* Parent process
* User
* Destination
* Command line

ProcessGuid was preferred when available.

## 5. Investigate Context

The analyst investigated surrounding activity to determine whether the behavior was:

* Expected
* Benign
* Suspicious
* Unconfirmed
* Potentially malicious

## 6. Assess Evidence

Individual events were not treated as definitive proof without supporting context.

The investigation considered both positive evidence and evidence that was absent.

## 7. Determine Disposition

Each case received an evidence-based disposition.

## 8. Document

The investigation was documented with:

* Findings
* Timeline
* Correlation results
* Evidence
* Limitations
* Final disposition
* Analyst lessons

# Evidence-Based Incident Classification

The investigations demonstrated several possible outcomes.

### Expected / Benign

Activity supported by sufficient context indicating legitimate or intentionally generated behavior.

Example:

```text
Test-NetConnection → PowerShell → 8.8.8.8:443
```

### Needs Context

Activity that requires additional information because available telemetry is incomplete.

Example:

```text
Network event → all-zero ProcessGuid → uncertain process attribution
```

### Suspicious

Activity containing indicators or context that justify additional investigation but do not yet establish maliciousness.

### Confirmed Malicious

Activity supported by sufficient evidence demonstrating malicious behavior.

No confirmed malicious activity was established in these Week 9 laboratory exercises.

# Telemetry Limitations

The investigations demonstrated several practical telemetry limitations.

## Process Attribution

Some network events contained all-zero ProcessGuid values.

## PID Reuse

A PID may be reused by different process instances.

Therefore:

```text
Same PID ≠ Same Process Instance
```

## Missing Correlation Events

Some ProcessGuids did not have corresponding network, file, or registry events in the available telemetry.

The absence of an event was therefore treated as a limitation of the available evidence rather than proof that the activity did not occur.

## Evidence Scope

All conclusions were limited to the telemetry available within the controlled laboratory environment.
